# DelegateChain

A hierarchical multi-agent system where work flows DOWN through capability tiers and critique flows UP, with each tier differentiated by scope (component → project → product → program → portfolio), ambiguity tolerance, autonomy, and time horizon. A router classifies the incoming task, delegates to the appropriate entry level, and each agent either delivers directly or decomposes the work and hands pieces to lower tiers. Parents review children's output against capability-appropriate rubrics before accepting and integrating. The system can execute both planning tasks (producing design documents) and code generation (producing tested implementations in an isolated workspace).

Most agent projects cannot show you what they built. This one can: six real components in `examples/` with tests and machine-generated design documentation, produced by the system itself.

---

## The Problem

Give a single agent a complex, ambiguous task and it will try to do everything — strategic framing, tactical decomposition, and mechanical implementation — all at the same temperature, all at the same altitude. Strategic work gets under-reasoned; implementation details bloat the context. You can decompose manually, but then *you* are the router, the delegator, and the quality gate.

The real problem is quality assurance across delegation. When a sub-task returns with an artifact, asking "is this good?" produces sycophancy. You need a rubric — scored criterion by criterion with evidence — calibrated to the capability level that produced the work.

And there is the routing problem. Not every task announces its altitude. "Improve extraction accuracy" could be component-level debugging or portfolio-level strategy depending on context.

So the system must route intelligently, delegate downward only, review against tier-appropriate rubrics, and integrate coherently. None of those alone is sufficient.

## Architecture

The system is organized around a **five-tier capability model** — an original design authored for this project, based on scope, ambiguity, and autonomy axes:

| Tier | Scope | Ambiguity | Autonomy | Time Horizon |
|:--|:--|:--|:--|:--|
| **Engineer** | Component | Well-scoped, clear requirements | Supervised | Days to weeks |
| **Senior** | Project | Some ambiguity, needs framing | Semi-autonomous | Weeks |
| **Staff** | Product | Significant ambiguity, multiple valid approaches | Autonomous | Months |
| **Principal** | Program | High ambiguity, cross-cutting concerns | Complete autonomy | Quarters |
| **Distinguished** | Portfolio | Emergent domains, unclear problem framing | Strategic autonomy | Multi-year |

Each tier has a YAML knowledge base defining:
- **Charter**: What this tier owns and how it operates
- **Altitude**: Scope / ambiguity / autonomy / time horizon
- **Pillars**: Invent / Implement / Influence capabilities
- **Performance rubric**: Criteria for reviewing this tier's output
- **Delegation rules**: What to keep, when to delegate down, when to escalate up
- **Model profile**: Which Bedrock model and temperature

### Why This Beats a Single Prompt

**Separation of concerns by capability.** Strategic framing (portfolio tier) runs at higher temperature with longer context. Tactical implementation (component tier) runs cooler with tighter focus. Mixing them dilutes both.

**Calibrated quality gates.** A senior agent reviewing an engineer artifact uses the *engineer rubric*: correctness, baseline engineering quality, appropriate escalation. Not "is this strategic?" — that's not what engineers do. The rubric matches the tier's charter.

**Delegation flows down, critique flows up.** An agent can delegate to any tier strictly below itself. `clamp_below()` enforces this: if an agent tries to delegate to its own level or above, the system corrects the target to the next tier down. Acyclic by construction.

**The router is part of the system.** Explicit `scope=component` → deterministic routing. Ambiguous task description → LLM classification against the scope and ambiguity ladders. Either way, work starts at the right altitude.

**Evidence: the system's output is visible.** Most agent frameworks produce chat transcripts. This one produces `examples/prime_numbers/`, `examples/dota/`, `examples/multi_kv/` — runnable code with test suites and design documents (COMPONENT_SPEC.md, COMPLEXITY_ANALYSIS.md, DELIVERY_SUMMARY.md) that were themselves generated by the chain. You can read the code it wrote.

### Delegation is Always Downward

The `clamp_below()` function is small but load-bearing:

```python
def clamp_below(delegator: Level, target: Level) -> Level:
    """Force target to be strictly below delegator."""
    if target.index >= delegator.index:
        return delegator.next_down()
    return target
```

If a Staff agent emits `target_level="staff"` (due to LLM error or ambiguous subtask), the orchestrator silently corrects it to Senior. No cycles, no peers, only downward.

### Review is Rubric-Based, Not Sycophantic

The naive approach: "Is this good? Yes/no."

The robust approach: Present the child's KB rubric criterion by criterion. For each:
- `id`: criterion identifier
- `criterion`: what "good" means for this tier
- `evidence_required`: what the reviewer must find
- `passed`: boolean
- `score`: 0-5
- `evidence`: quoted text from artifact
- `comment`: why it passed or failed

If evidence is missing or weak, the criterion fails. Confident prose without substance does not pass.

## Running

### Setup

```bash
bash setup.sh
source .venv/bin/activate
```

**Requirements:**
- Python 3.11+
- AWS credentials with Bedrock access (Claude Sonnet 4.5)
- Bedrock Anthropic models enabled in your region

```bash
# Verify credentials
aws sts get-caller-identity
export AWS_DEFAULT_REGION=us-east-1
```

### Planning Mode (Design/Strategy)

```bash
# Run a task through the full delegation chain
delegate-chain --task "Design a bilingual PDF classification pipeline"

# Force an entry tier (skip the router)
delegate-chain --task "Implement a precision-recall evaluator" --entry-level engineer

# Increase review retry limit and cap sub-task fanout
delegate-chain --task "Define a compliance monitoring strategy" --max-iters 3 --max-fanout 4
```

### Code Generation Mode

The `build/` sub-system uses the same KB and tier model to produce runnable code:

```bash
# Generate a new component with tests
python -m delegate_chain.build.run \
  --task "Create a Python module is_prime(n) with pytest tests" \
  --workspace ./build_out

# Generate with an existing repo as context
python -m delegate_chain.build.run \
  --task "Add error handling to the kvstore module" \
  --workspace ./build_out \
  --ingest ./examples/multi_kv

# Edit an existing repo (produces a reviewed diff, original untouched)
python -m delegate_chain.build.run \
  --task "Add type annotations to all public functions" \
  --edit ./myrepo \
  --apply
```

### Inspection (No API Calls)

```bash
# View the system prompt for each tier
delegate-chain --print-prompts

# View one tier only
delegate-chain --print-prompts --level senior

# See the tier ladder and KB summary
delegate-chain --list-kb

# Audit the KB before spending anything on Bedrock (exit 1 on errors; --strict also fails on warnings)
delegate-chain --check-kb
delegate-chain --check-kb --strict --format json
```

The runtime reads the KB leniently, so most KB mistakes do not crash a run. They quietly
change it. A misspelt `bedrock_model` is sent to Bedrock as a raw model id and priced at the
default model's rate. An unknown skill id is printed into the prompt as its bare id. An unknown
proficiency rung, scope or autonomy value is printed with an empty definition. A tier with no
`performance_rubric` gives its reviewer nothing to score. `--check-kb` names each of these as an
error, and also checks the org chart that delegation and review depend on (`manages` is every
tier below, `reports_to` is the tier directly above). It warns when the ladder runs backwards
(scope, autonomy or a skill's proficiency dropping one tier up) and when a definition kept in
two places has drifted. CI runs it with `--strict`.

On the shipped KB it passes clean, and it lists the taxonomy skills no tier claims (currently
18 of 29, mostly the ML, data and ops skills). That is informational, not a failure: it shows
how much of the taxonomy the agent prompts actually ask for.

## Testing

```bash
# Full suite
pytest

# Pure logic (no I/O)
pytest tests/unit -v

# Delegation chain, router, cost tracking
pytest tests/integration -v

# Coverage
pytest --cov=delegate_chain --cov-report=term-missing

# Live eval: rubric discrimination + revision recovery (requires Bedrock)
python -m delegate_chain.eval.gate_check --profile default
```

The orchestrator tests use a `MockLLM` that returns canned JSON without touching Bedrock. Because `deliver()`, `review()`, and `integrate()` are pure request/response functions, the full delegation logic runs exactly as in production with a mock. Testing "senior delegates to engineer" means configuring the mock to return `mode=delegate` on the first call and `mode=solve` on subsequent calls.

`gate_check.py` is the live eval: it presents a senior agent with four synthetic engineer artifacts (one good, three bad: fabricated metrics, altitude overreach, policy violations). It asserts the good one passes and the bad ones fail. Then it seeds a bad artifact, captures the failure feedback, feeds it back to an engineer agent as a revision request, and checks that the revised artifact passes. This verifies the review loop is discriminating, not rubber-stamping.

## Configuration

AWS credentials via boto3's profile chain:

```bash
export AWS_PROFILE=my-bedrock-profile
delegate-chain --task "..."
```

Or inline:

```bash
delegate-chain --task "..." --profile my-bedrock-profile --region us-east-1
```

When `--profile` is set, the client drops ambient `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` from the environment so profile credentials take precedence.

Response cache is on by default (`.delegate_cache/`). Cached calls cost $0. Disable with `--no-cache`.

Per-tier model assignments are in each KB YAML:

```yaml
model_profile:
  bedrock_model: claude-sonnet-4-5
  max_tokens: 8192
  temperature: 0.2
```

Higher tiers use slightly higher temperature (0.2 → 0.4) reflecting the expectation that strategic framing benefits from variation while implementation benefits from consistency.

## Limitations and Scope

**LLM provider and models required.** The system requires AWS Bedrock access with Claude Sonnet 4.5 (or compatible Anthropic model) enabled in your region. It will not run without credentials. The knowledge base and rubrics are written for Claude's instruction-following style; other providers would require tuning.

**Output quality varies with input.** A well-framed task with explicit scope produces a tight delegation tree. An ambiguous task forces the router to classify, which can misroute. Garbage in, garbage out — but the rubric review catches some categories of garbage before integration.

**Design documents in `examples/` are machine-generated.** COMPONENT_SPEC.md, DELIVERY_SUMMARY.md, SENIOR_REVIEW_RESPONSE.md — all written by the system during code generation runs, not hand-authored. Framed correctly this is a strength: the system demonstrates its own capability by shipping its output. But a reviewer expecting human-written docs will notice the style.

**The capability model is original to this project.** The five tiers (engineer / senior / staff / principal / distinguished) are differentiated by scope, ambiguity, autonomy, and time horizon. This is an authored design, not derived from any employer's leveling framework. The knowledge base was rewritten from first principles as a generic capability model for hierarchical delegation.

**Sibling sub-tasks execute sequentially.** They are independent by construction (a delegation batch is split so pieces don't depend on each other), so parallel execution would cut wall-clock time by the fanout factor. Not implemented; the orchestrator is synchronous Python.

**No interruption recovery.** The artifact tree lives in memory. A crash loses the tree. At depth 5 with fanout 4 this is manageable; a persistent checkpoint would be required for resumable long-running chains.

## Tradeoffs and Decisions I Made Along the Way

**The schemas are pure data, and that was the right starting point.** `Task`, `Artifact`, `ReviewVerdict` — all frozen dataclasses with no methods that touch the LLM, filesystem, or clock. `deliver()` takes a Task and returns a dict. `review()` takes an Artifact and returns a ReviewVerdict. The entire orchestrator is wiring. The payoff: `MockLLM` just needs to return JSON in the right shape, and the full delegation and review logic runs without modification. Mixing measurement with decision-making is the root cause of most untestable multi-agent code; separating them cost nothing here.

**`clamp_below()` is four lines but it's load-bearing.** Early iterations didn't enforce that delegation targets must be strictly below the delegator. An agent would emit `target_level="staff"` from a staff agent — model error or ambiguous charter phrasing — and create a cycle. Clamping handles it silently: if target is at or above the delegator, redirect to the next level down. Combined with logging (`capping fanout`, depth-limit warnings), the tree's shape becomes visible during runs, which is how I caught poorly-worded sub-tasks causing repeated same-level delegation.

**Shrink-fast-grow-slow thinking applies to tree shape, not just numeric sizing.** AdaptiveFetch uses it for batch sizing: cut on pressure, grow after patience. Same logic here for decomposition aggressiveness. `max_fanout` caps sub-tasks per node. Without it, a staff agent handed an ambiguous product-scope task can emit ten sub-tasks, each of which also delegates, and cost grows factorially. The cap isn't about correctness — it's about asymmetry: being too aggressive costs the whole run, being too conservative costs coverage. Default is conservative.

**Why the LLM is in the review loop and not just the delivery loop.** The easy architecture: LLM decomposes, rules engine checks output against a schema. That works for format validation. It doesn't work for quality validation. Whether an engineer artifact contains "a rigorous evaluation with unit tests and explicit methodology" isn't a JSON schema check — it requires reading and judging. The rubric structures the judgment (criterion by criterion, evidence required), but the model provides it. This is where LLMs add value over deterministic checks; using them only as orchestrators wastes that.

**Rubric-based review versus "is this good?" isn't minor.** The naive prompt: "Does this meet the bar? Yes/no." That produces rubber-stamping at uncomfortable rates. The rubric forces the reviewer to confront each criterion individually, cite concrete evidence from the artifact, and explain why evidence satisfies the criterion. The instruction "if evidence is missing or weak, the criterion fails — do not reward confident prose without substance" appears verbatim in `build_review_prompt()` because I found the model needed explicit instruction that assertion isn't evidence. Promotion-signal tracking emerged from the same structure: if the rubric already grounds review in criteria, appending "tag next-level criteria this work hints at" adds almost nothing to prompt cost while giving a signal you'd otherwise extract separately.

**Bottom-up review is the right direction.** The alternative: top-down verification — once you have the tree, a senior reviewer walks down and checks everything. The problem is context. When a staff agent delegates to senior, it writes `kept_work` explaining framing, design decisions, and why this sub-task was handed down. The staff agent is the only entity with both framing context and the full child artifact — it's the natural reviewer. A distinguished agent reviewing raw engineer output at the leaves has neither the sub-task framing nor calibrated expectations for engineer-level work. The KB review loop follows the reporting line because the reporting line is exactly the right scope: one level up, who delegated the work, who knows what "good" looks like at that level.

**The revision loop is bounded and I keep it tight.** `max_review_iters=2` by default: each child node gets at most three attempts (original delivery, two revision passes). Why not higher — if the model can revise, why not iterate until it passes? Two reasons. First, if a child fails twice on the same criteria, the problem is usually mis-scoping or conflicting rubric criteria, not insufficient attempts. More retries don't fix structural problems. Second, cost. Each revision is another LLM call for deliver plus review. At depth 3 with 4 sub-tasks each, generous `max_review_iters` compounds quickly. The gate_check eval confirms a good artifact passes first try and a genuinely bad artifact fails both times — revision is for recoverable failures, not fundamental ones.

**Cost tracking per node was the right granularity.** The orchestrator accumulates `total_cost_usd` globally, and each Artifact node has its own `cost_usd` for its LLM calls (deliver + review + integrate). Per-node cost lets you read the printed tree and immediately see which nodes are expensive. In practice, the router and review calls are cheap (short prompts); the expensive calls are `integrate()` at high tiers where the context fills with all children's summaries. Knowing `staff.integrate()` cost $0.04 of a $0.06 total run tells you where to optimize. The disk cache eliminates repeat costs during iteration — running the same task twice costs nothing after the first run.

**The KB in YAML is a configuration boundary, not a code boundary.** Every agent's charter, altitude, delegation rules, skills, rubric, and promotion signals live in YAML per tier. `build_system_prompt()` translates YAML to structured natural-language system prompt; agent code never sees YAML directly. Changing what a senior does — adding a rubric criterion, adjusting ambiguity definition, swapping a model — is a config edit, not a code change, and doesn't require a test run to validate in isolation. Downside: the KB isn't type-checked. A typo in a YAML key silently becomes an empty string in the system prompt. Smoke tests in `test_kb.py` load every level file and assert critical fields are non-empty, catching the most likely authoring mistakes.

**The build sub-system is separate and I kept it separate.** `build/` contains a LangGraph pipeline that generates runnable, tested code: plan → implement → run tests → review → iterate. It shares the `KnowledgeBase` and `BedrockLLM` client but has its own agent (`ToolAgent`) that runs a tool-use loop rather than the single-shot deliver/review pattern. The two sub-systems answer different questions. Deliver/review answers "how do you decompose a complex task across capability levels?" — artifact is text. Build answers "how do you generate runnable, tested code?" — artifact is files on disk. Keeping them separate means each evolves without contaminating the other.

**What I'd change at scale.** Sibling sub-tasks execute sequentially because the orchestrator is synchronous Python. They're independent by construction, so parallelism would cut wall-clock time by the fanout factor. The artifact tree lives in memory; a persistent store would handle interruptions and resume. The router uses a full Sonnet-4.5 call for ambiguous tasks; a Haiku-class classifier tuned on labeled examples would do the job at a fraction of cost. The revision loop is blind to *why* a failure happened — it passes the full feedback string but doesn't distinguish "wrong approach" from "missing tests" from "altitude overreach." A structured failure taxonomy in the rubric output would let the re-issue prompt be more targeted.
